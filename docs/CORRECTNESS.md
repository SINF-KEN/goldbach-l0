# Correctness: the argument, its invariants, and how each is enforced

This document states what a `result=PASS` of `goldbach_l0` means, why the
dense production path earns it, which assumptions that argument rests on,
and where each assumption is checked. Implementation details live in
[PROJECT-REFERENCE.md](PROJECT-REFERENCE.md); function-level contracts
(`@pre` / `@post`) are in the source. Last full audit: v2.3.0 (2026-10-06).

## 1. The claim

For every even `n` with `max(start, 4) <= n <= limit` (start rounded up to
even), `goldbach_l0` exits 0 with `result=PASS` only if it has exhibited a
partition `n = p + q` with `p` and `q` prime. Any failure — a Level Zero
error, a device error flag, a buffer overflow, an unreadable statistics
state, or a genuine counterexample — makes it exit non-zero without
printing PASS. Empty or reversed ranges are usage errors (exit 2).

## 2. The mathematical argument

**Witnesses.** For each even `n` the GPU tests candidates `p` from a fixed
list of odd primes `p <= MAX_GB_PRIME = 9781` (generated, not hard-coded) and
reads one bit of a prime map for `q = n - p`. An even counts as resolved by
the GPU only through such a test. Evens the GPU cannot resolve are returned
in a leftover list and settled on the CPU by deterministic Miller–Rabin
(bases 2..37, exact for all 64-bit integers — Sorenson & Webster, ψ12 >
3.3e24), first over the candidate list, then over every odd `p <= n/2`
(so an even needing `p > 9781` — a new record — is found, not failed).

**The prime map.** The map stores one bit per odd `q` coprime to 30 in the
segment's q range, as eight class arrays (`q = 1, 7, 11, 13, 17, 19, 23,
29 mod 30`). A set bit must mean `q` is prime:

- every composite `q <= limit` has a prime factor `<= sqrt(limit)`; the
  base-prime list holds every odd prime `<= floor(sqrt(limit)) + 16`
  (`base_prime_bound`, saturating at 2^32 - 1);
- multiples of 3 and 5 are not stored; every multiple of 7 .. 61 is cleared
  by whole-word mask tables (the primes themselves are restored);
  base primes below the split (~430K) clear every odd multiple from `p^2`
  in the tile kernel; the larger base primes (packed kernel, hit lists)
  clear `p * m` only for multipliers `m` coprime to 30030, from
  `max(p^2, first odd multiple >= q_first)`. This is complete: a composite
  `q` with smallest prime factor `s` has `q >= s^2`; if `s <= 61` the masks
  clear it, if `s` is below the split the tile walk does, and otherwise
  `q = s * m` with every prime factor of `m` at least `s >= 67`, so `m` is
  coprime to `2 * 3 * 5 * 7 * 11 * 13 = 30030` and `s` clears it;
- marks start at `p^2`, so a base prime that lies in the map keeps its bit.

**Soundness asymmetry.** A prime wrongly cleared ("false composite") can
only hide a witness; the even then goes to the exact CPU fallback, so the
verification stays correct (the statistics would not). A composite wrongly
kept ("false prime") could credit an even with a non-witness. Every map
invariant below is therefore checked in the direction that matters:
nothing composite may survive.

**Crediting.** The checker credits even `n = seg_start + 2e` through
candidate `p` only by reading the map bit of `q = n - p`; the dense bit is
`b = e + (seg_start - q_first - p) / 2` — the numerator is even (even - odd
- odd), so the shift is exact even when negative — and a `q` outside the
map counts as a miss.

**Coverage.** Segments start `segment_even` apart and end at
`seg_start + segment_even - 2`, so their evens tile `[start, limit]`
without gap or overlap (the last segment absorbs a remainder of exactly one
span: one extra even). Every even of a segment is either resolved by phase
A, appended to the pending list, resolved by phase B, or appended to the
leftover list — no other outcome exists in `check30_a` / `check30_b`.

## 3. Invariants and where they are enforced

| Invariant | Enforced by |
|---|---|
| `limit <= 2^64 - 2^40` (host first-hit sums stay below 2^64) | `require_supported_limit`: throws before any GPU work |
| a segment's odd count `< 2^32` (all kernel offsets are u32) | host: "segment span too large" before GPU work (verified with `--segment 9e9`) |
| base primes = exactly the odd primes `<= bound` | generated by a segmented sieve; a disk cache is used only if its header matches **and** the payload passes the content check (odd primes < 64 first, strictly ascending odd, `<= bound`); caches are published atomically (temp + fsync + rename) |
| pending list not overflowed | kernel counts past the cap; host throws if `pending_count > pending_cap` (every segment, incl. the last) |
| leftover list not overflowed / valid | host throws if `count > MAX_LEFTOVERS` or any index `>= seg_evens` |
| hit lists / bucket ring not overflowed | kernels set an error flag; host throws |
| hit-list 32-bit walk | host throws unless `q_odds_full < 2 delta`, `2 delta < 2^32`, `delta + p_max < 2^32` |
| `mod_ff` remainder fits int32 | proven bound `|q - floor(x/p)| <= (x/p) 2^-46 + 1`; CPU emulation of 1.4e7 (x, p) pairs: max \|r\| = 5.4e8 < 2^31; guarded fix-up loops make the result exact |
| float fast paths exact (`MED_F32`, `OWN_F32`, `OH_F32`) | uniform guards (`p < 2^23`, offsets `< 2^24` / `< 2^17`, `y < 2^32`); remainders stay below 2^24 so `fma` is exact |
| `map_clear_w` marks only q coprime to 30 | every caller marks multiplier-wheel / CP15015-filtered q only |
| tile stores before large-prime atomics | explicit barriers (an event wait alone was observed insufficient on this driver) |
| statistics merged exactly once | state re-read under an exclusive lock at commit; a range overlapping covered ranges is not merged; a damaged, truncated or incompatible (`tail_t`) state is refused; the write is atomic and fsync'd before the run returns |
| journal chain intact | `run_range.sh` and the CI follow PASS rows only if their own `start=` / `limit=` agree; malformed rows are ignored |

## 4. Validation that exercises the invariants

| What | Checks |
|---|---|
| `debug_map` (tools) | the complete map (masks + tile + large primes) vs Miller–Rabin on real ranges incl. two full production segments at 4e18 and 5e18 |
| `GB_BUCKET_VERIFY=1` | every segment's map vs a rebuild with the packed kernel over **all** large primes (hit lists and the ring), word for word |
| `debug_check_hi` (tools) | every checker vs a per-even reference on random maps in production geometry; mutations fail |
| `stats_ref` vs GPU (`gpu_validate.sh`) | exact prime / twin counts, p(n) histogram and first occurrences at 1e12, 4e18, 4.4e18, 5e18, across 2^63 and at 2^64 - 2^40 |
| local CI per production slice | re-verifies a full slice and checks its prime count against an independent primecount |
| `known_windows.py` (in `gpu_validate`) | prime counts, max p(n) and its n against an independent verifier's published windows (GoldbachGPU v3.2.0: CUDA, byte sieve, other hardware) at 4e18 + 1e10 .. 1e13 and 1e12 across 2^63; `campaign` mode checks the production state / log against the same windows (to 4e18 + 1e15) once covered |
| `host_tests` | Miller–Rabin vs all 10403 base-2 Fermat pseudoprimes below 2^32 and ψ1..ψ11 (optionally Feitsma's full list below 2^64); prime lists, cache (incl. damaged payloads), Miller–Rabin, masks, plans, statistics state (merge, overlap, concurrency, damage) — each regression mutation-tested |
| `cli_tests`, `test_ci` | the CLI range contract; the journal chain rules |

## 5. Audit of v2.3.0 (2026-10-06): findings

Fixed (each with a regression test that fails on the old code):

1. Statistics state could lose a concurrent run's totals, survive
   truncation silently, merge across tail thresholds, ignore a failed write
   and skip fsync (`gstats.hpp`). Exact data loss / corruption risk for the
   campaign's statistics; verification unaffected.
2. Prime cache written in place: concurrent builders could expose a
   zero-filled hole to a third reader (false primes). Load checked the
   header only.
3. Leftover indices were not range-checked: a corrupted list would have
   verified the wrong `n` while the unresolved even went unchecked.
4. `start > limit` verified `n = limit` (outside the request) and passed;
   an odd `start == limit` failed with an unrelated error.
5. `MED_F32` guard allowed primes below 2^24, but the exactness argument
   needs `p < 2^23` (unreachable in production: split primes ~430K).
6. Journal rows were trusted field by field: a damaged slice end could
   have skipped unverified evens; a cut-off row crashed the CI reader.
7. The CI built against the live (possibly uncommitted) goldbach-tools tree.
8. `is_prime_trial` overflowed `d * d` above (2^32 - 1)^2 (unreachable in
   practice); `--split` was silently truncated to 32 bits.

Checked and found correct (not changed): class-map geometry and phases;
host first-bit formulas (dense and class); `check30_b` crediting
arithmetic; pending / leftover overflow handling; the segment-span guard;
`mod_ff` exactness (its code comment's tighter claim was wrong for small
`p` and is corrected); `count30` limits and lane coverage; Level Zero error
propagation (every call through `ZE_CHECK`).

## 6. Remaining assumptions and risks (not proven here)

- **`MAX_GB_PRIME` as candidate bound** is an empirical fact below 4e18
  (Oliveira e Silva); above it the CPU fallback scans further, so a larger
  `p(n)` is found, not missed.
- **Driver and compiler behaviour**: the barrier requirements and the
  in-order list are empirical on NEO / IGC 26.31–26.35; a driver update
  must re-run `gpu_validate.sh` (and `GB_BUCKET_VERIFY=1`).
- **Kernel functions not used in production** (legacy checker modes,
  `--sparse`) were audited for fail-closed behaviour, not line by line.
- **Non-default `-D` switches** in `goldbach.cl` keep superseded code paths
  for A/B; CI compiles only the defaults, so those branches may rot.
- **`mod_ff` bound**: proven up to the ~46-bit float-float estimate and
  measured by emulation; the GPU's own rounding is not bit-identical to the
  emulation (it may contract or approximate the reciprocal), which the
  4x margin to the int32 limit absorbs.
- The statistics' correctness relies on `stats_ref` agreement on sampled
  windows plus the CI's per-slice primecount; a fault in a non-sampled
  segment's p(n) histogram (sampled segments only) would not be caught.
